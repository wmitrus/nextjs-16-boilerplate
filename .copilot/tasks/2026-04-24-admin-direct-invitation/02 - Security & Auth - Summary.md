## Security Findings

### CRITICAL — API-Level Admin Authorization Gap (pre-existing, must not repeat)

**Finding**: Existing `/api/admin/waitlist/[id]` uses only `withNodeProvisioning`. `withNodeProvisioning` checks that the user is authenticated and provisioned (has a tenant membership) — it does NOT verify admin role. Any authenticated tenant member can call admin API endpoints directly.

**For new admin invitation routes**: Admin authorization MUST be enforced at the API layer, not just the layout layer. The layout guard is a UX guard; the API must be independently secure.

**Required pattern for admin API routes:**

```typescript
// After withNodeProvisioning resolves access, check admin:
const userEmail = access.identity.email;
const isAdmin =
  isEnvBasedPlatformAdmin(userEmail) ||
  (await authzService.can({ ... SECURITY_MANAGE_POLICIES ... }));
if (!isAdmin) {
  return createServerErrorResponse('Forbidden', 403, 'FORBIDDEN');
}
```

### REGISTRATION_MODE must not block admin invitations

**Finding**: The existing `POST /api/auth/invite` route does not check `REGISTRATION_MODE`. Admin direct invitations must similarly bypass `REGISTRATION_MODE=invite-only` — admins can always invite, regardless of registration mode.

**Constraint**: No `REGISTRATION_MODE` check in admin invitation routes.

### Role validation — roleId must belong to the organization

**Finding**: If admin supplies a `roleId` from a different organization, they could assign cross-org roles. The route must validate that the `roleId` belongs to the `organizationId` before creating the invitation.

**Required**: Query `rolesTable WHERE id = roleId AND organizationId = orgId` before calling `createInvitation()`. If not found → 400.

### Duplicate invitation — correct error handling

`createInvitation()` throws `DuplicateInvitationError` when a pending invitation already exists for email+org. Admin routes must catch this and return 409, not 500.

### Input validation

- `email`: Zod `z.email()` — required
- `roleId`: Zod `z.uuid()` — required
- `id` param (revoke): must be a valid UUID — validate before DB call

### Token security

Invitation tokens are generated by `generateInvitationToken()` in `src/modules/invitations/domain/token.ts`. These are not guessable and expire. No change needed.

### Information disclosure — list endpoint

`GET /api/admin/invitations` returns all org invitations. This is admin-only (guarded as above). The response should include `email`, `status`, `expiresAt`, `createdAt` — not the raw `token` field (tokens should not be exposed via the list API).

### No REGISTRATION_MODE bypass needed for the accept flow

The existing `/auth/invite/[token]` accept flow already works independently of `REGISTRATION_MODE`. No change required there.

## Authorization Model Decision

**Admin invitation permission model:**

- Admin can invite (bypasses `USER_INVITE` ABAC check) — admin role itself implies this
- Admin check at API level: `isEnvBasedPlatformAdmin(email)` OR ABAC `SECURITY_MANAGE_POLICIES`
- Do NOT use `USER_INVITE` action as the gate — that is for regular member invite (existing `/api/auth/invite` route)
- Admin invite is a superset operation gated on `SECURITY_MANAGE_POLICIES` (same gate as admin panel access)
